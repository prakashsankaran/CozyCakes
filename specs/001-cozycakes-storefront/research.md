# Research: CozyCakes Storefront

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-20

Each decision lists what was chosen, why, and what else was considered. Library versions are the
latest stable releases at implementation time unless a task says otherwise.

## 1. Application framework

- **Decision**: Next.js 16 (App Router, Cache Components and Partial Prefetching enabled) with
  React 19 and TypeScript, as one deployable web app. Database reads sit behind `connection()` inside
  `<Suspense>`, so the static shell prerenders at build time without a database and catalog data
  streams in at request time (briefly cached with `"use cache"`).
- **Rationale**: Server rendering and streaming give fast first paint on phones (Principle V);
  server components keep pricing/availability logic on the server (Principle IV); route handlers
  provide the versioned HTTP API a mobile app needs (Principle III); very large ecosystem.
- **Alternatives**: Remix/React Router (good, smaller ecosystem for commerce); Astro + islands
  (great for content, weaker for app-like flows); a separate SPA + API (two deployables, rejected
  by Principle VI).

## 2. Repository layout for a future mobile app

- **Decision**: pnpm workspaces + Turborepo monorepo: `apps/web` now, `apps/mobile` later;
  shared `packages/core` (domain logic + zod schemas), `packages/db`, `packages/design-tokens`.
- **Rationale**: The mobile app (planned as Expo / React Native) can import the same domain rules,
  schemas, and tokens, and call the same `/api/v1`. Keeps one source of truth.
- **Alternatives**: Single Next.js project (simpler now, painful extraction later); Nx (heavier
  than needed).

## 3. Styling, components, and motion

- **Decision**: Tailwind CSS v4 themed from `packages/design-tokens` (its `tokens.css` is a Tailwind
  `@theme`); accessible headless primitives (Radix UI) for dialogs, sheets, selects once needed;
  CSS keyframe animations plus React's `<ViewTransition>` for the card → detail morph, all disabled
  under `prefers-reduced-motion`; Motion (formerly Framer Motion) is added only when the builder
  (US2) needs physics or gesture-driven animation; `next/font` for self-hosted fonts.
- **Update 2026-10-20 (storefront build)**: CSS + `<ViewTransition>` covered every US1 delight moment
  with zero extra JavaScript, which protects the performance budget, so Motion was not installed yet.
- **Rationale**: Tokens keep web and mobile visually consistent (Principle II); headless primitives
  give WCAG-compliant behaviour while allowing a fully custom, non-template look; Motion supports
  layout and shared-element transitions needed for the "cake assembles" builder and sheet cart.
- **Alternatives**: A pre-styled kit (MUI, Chakra) looks too generic for the brand; CSS-in-JS
  runtime libraries hurt performance.

## 4. Brand direction (placeholder until owner assets arrive)

- **Decision**: Palette: cream `#FFF8F0` base, cocoa `#3B2420` text, blush `#F4B6C2` and caramel
  `#D9925B` accents, pistachio `#A8C99B` for success. Type: an expressive soft serif for display
  (e.g., Fraunces) and a rounded sans for text (e.g., Nunito Sans). Large radii (20–28px), soft
  shadows, grain texture on hero sections.
- **Rationale**: "Cozy" suggests warmth, softness, and home baking. The Instagram page could not
  be fetched from the build environment, so these are inferred from the name and must be checked
  against the real logo and photography.
- **Alternatives**: Dark luxury patisserie look (too formal for "cozy"); bright pastel candy look
  (risk of feeling childish).

## 5. Database and ORM

- **Decision**: Managed PostgreSQL (e.g., Neon or Supabase free tier) with Drizzle ORM, the
  `postgres` (postgres.js) driver, and versioned SQL migrations generated by drizzle-kit.
- **Rationale**: Relational data (orders, items, capacity) needs transactions and row locks for
  "no overbooking" (SC-005). Drizzle is lightweight, type-safe, and serverless-friendly.
- **Alternatives**: Prisma (heavier client, fine alternative); a headless commerce SaaS such as
  Shopify/Medusa (strong for standard retail, but the made-to-order capacity calendar and custom
  builder would fight the platform and the look would drift toward conventional).

## 6. Payments

- **Decision**: Razorpay (Orders API + Checkout + webhooks + refunds) behind a `PaymentProvider`
  interface in `packages/core`.
- **Rationale**: Assumed India/INR (spec Assumptions): Razorpay supports UPI, cards, netbanking
  and wallets, hosted checkout (no card data on our servers, Principle IV), signed webhooks, and
  refunds via API. The interface allows switching to Stripe if the business is elsewhere.
- **Alternatives**: Stripe (best developer experience; UPI and India onboarding more limited);
  Cashfree/PhonePe PG (viable Indian alternatives).
- **Open**: Owner to confirm country and which merchant account the business will hold.
- **As built (US3, 2026-10-20)**: checkout registers a Razorpay order for the server-priced total,
  opens Razorpay's hosted checkout, and confirms the order when the browser returns the signed
  result (`order_id|payment_id` HMAC with the key secret). The `payment.captured` webhook confirms
  the same order idempotently in case the tab closes. Checkout is only switched on when
  `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are set. A test provider (`PAYMENT_PROVIDER=test`,
  refused on Vercel production) signs fake payments the same way for end-to-end tests.
- **As built (US4, 2026-10-21)**: cancelling an order refunds the full payment through Razorpay's
  refunds API (`POST /v1/payments/{id}/refund`, normal speed). The refund is attempted after the
  cancellation is saved, so a refused refund never leaves a paid order stuck; the owner is told to
  refund it from the Razorpay dashboard.

## 7. Preventing overbooking

- **Decision**: Each checkout creates a `CapacityHold` for the chosen date inside a transaction
  that locks that date's `DayAvailability` row (`SELECT … FOR UPDATE`) and counts confirmed
  orders + unexpired holds. Holds expire after 15 minutes. The payment webhook converts the hold to
  an order idempotently (unique provider payment id).
- **Rationale**: Guarantees SC-005 and SC-006 with plain Postgres, no extra infrastructure.
- **Alternatives**: Redis locks (extra service, Principle VI); optimistic retry only (race-prone).
- **Known risk**: holds are taken before payment, so someone scripting checkouts could keep dates
  looking full for 15 minutes at a time. Acceptable at launch; if it happens, cap open holds per
  visitor or IP.

## 8. Authentication

- **Decision**: Better Auth with email one-time codes for customers and staff; staff flagged by
  role; sessions via secure HTTP-only cookies on web and bearer tokens for the future mobile app.
- **Rationale**: Passwordless matches FR-027 and is friendlier on phones; first-class support for
  both web cookies and Expo clients.
- **Alternatives**: Auth.js (mature, weaker native-app story); Clerk (fast, but per-user cost and
  external UI).
- **As built (US5, 2026-10-20)**: 6-digit codes, valid 10 minutes, 5 attempts, stored hashed. The
  owner is whoever's address is in `OWNER_EMAIL` (comma-separated), checked on every request, so
  the owner can never be locked out and no address lives in the repo. Until customer accounts
  (US6), codes are only emailed to the owner and staff; the form gives everyone the same answer so
  it doesn't reveal who has access. Sessions are signed with `BETTER_AUTH_SECRET`, or, when unset,
  a secret derived from `DATABASE_URL` (already a server-only secret), so there is one less setting
  to manage. `proxy.ts` only redirects visitors without a session cookie; the role check runs on
  every back-office page and Server Action (`apps/web/lib/admin/dal.ts`).

## 9. Images and uploads

- **Decision**: Cloudinary for cake photos and customer reference uploads (signed direct uploads,
  automatic format/size transforms), rendered through `next/image` with a Cloudinary loader.
- **Rationale**: Responsive, optimised images are the biggest lever for LCP on a photo-heavy site.
- **Update 2026-10-20 (US2)**: Configured by one `CLOUDINARY_URL` variable. Reference uploads are
  signed per file (fixed `public_id`, `allowed_formats` jpg/png/webp/heic) and served with
  `f_auto` so HEIC photos display everywhere. The 10 MB limit is checked on the device and in the
  signing request; a Cloudinary upload preset can enforce it at the edge later. Without the
  variable the builder's photo step points customers to Instagram instead.
- **Alternatives**: S3/R2 + own resizing (more work); Vercel Blob (no transforms).

## 10. Notifications

- **Decision**: Transactional email via Resend with React Email templates. Notification sending
  goes through a `Notifier` interface so WhatsApp (Meta WhatsApp Cloud API or an Indian BSP) can be
  added without touching order logic.
- **Rationale**: Email is reliable and cheap for MVP; WhatsApp is how this audience already talks
  to the baker, so the seam is designed in now.
- **As built (US5)**: sign-in codes go through Resend's HTTP API with `fetch` (no SDK). Without a
  verified domain, `EMAIL_FROM` defaults to Resend's shared test sender, which can only email the
  Resend account's own address: enough for the owner to sign in. `MAIL_OUTBOX_DIR` writes emails to
  JSON files instead, for local development and end-to-end tests.
- **As built (US3)**: order confirmation and new-order emails are plain HTML strings sent the same
  way; React Email templates and the `Notifier` seam come with WhatsApp/SMS.
- **As built (US4)**: status updates (FR-019) are emails in the same style, each linking to the
  private order page. That page also re-reads the order every minute while it is open, so it stays
  current without push notifications.

## 11. Delivery area

- **Decision**: The baker configures a list of serviceable postal codes (PIN codes), each with a
  delivery fee. Pickup is always available.
- **Rationale**: Far simpler and more predictable than geocoding and radius maths; PIN codes are
  how Indian customers think about delivery areas.
- **Alternatives**: Radius from kitchen via a maps API (cost, API keys, address-quality issues).

## 12. API shape

- **Decision**: REST JSON under `/api/v1`, request/response schemas defined once in zod in
  `packages/core`, OpenAPI document generated from them. Web server components call the same
  service functions directly; client components and the mobile app use HTTP.
- **Rationale**: Principle III; one schema for validation, types, and docs.
- **Alternatives**: tRPC (great for web-only, awkward for a native client and third parties);
  GraphQL (more machinery than needed).

## 13. PWA

- **Decision**: Web app manifest with standard and maskable icons, plus a small hand-written service
  worker (`apps/web/public/sw.js`) that precaches a branded `/offline` page and serves it when a
  navigation fails. Serwist is adopted later if runtime caching of pages and images is needed.
- **Rationale**: Meets FR-029 with ~30 lines and no build plugin; Next.js 16's Turbopack build needs
  extra Serwist configuration that isn't justified yet (Principle VI).

## 14. Testing and quality tooling

- **Decision**: Vitest for unit tests (pricing, lead time, capacity, order state machine); Playwright
  for e2e across a phone and a desktop viewport; `@axe-core/playwright` for accessibility; Lighthouse
  CI with the Principle V budgets; ESLint + Prettier + `tsc --noEmit`; GitHub Actions runs all.

## 15. Hosting and cost

- **Decision**: Deploy the web app on Vercel (preview deploys per PR). Note that Vercel's free Hobby
  plan is for non-commercial use, so production should be on the Pro plan or an equivalent host
  (e.g., Netlify or Cloudflare); database, Cloudinary, and Resend start on free tiers.
- **Rationale**: Zero-ops, preview links let the owner review UI changes from a phone.
- **Update 2026-10-20 (deployment)**: The owner connected the repo to Vercel (root directory
  `apps/web`). The database is Neon Postgres created from Vercel's Storage tab, which injects
  `DATABASE_URL` without anyone handling the secret. `apps/web/vercel.json` runs
  `scripts/vercel-build.sh`: apply migrations, load the sample menu when the catalog is empty or
  holds an older sample menu than `SAMPLE_MENU_VERSION` (`db:seed --if-outdated`), then
  `next build`. Until US5 every cake is placeholder data, so reloading it is safe; T083 retires
  the reload once the baker manages the real menu.
- **Docker**: Postgres in Docker is for local development only (`docker-compose.yml`); Vercel cannot
  run or reach a container, so it is not an option for the hosted site.
- **Known trade-off**: preview deployments share the production database for now. Before real orders
  exist (US3), give previews a separate Neon branch so PR migrations cannot touch live data.

## 16. Time zone

- **Decision**: A single bakery time zone setting (default `Asia/Kolkata`). Fulfilment dates are
  stored as calendar dates (no time) plus a slot; "today" and lead-time cut-offs are computed in the
  bakery time zone on the server.
